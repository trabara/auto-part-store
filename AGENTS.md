# AGENTS.md — Coding Agent Reference

ERP SaaS on Medusa v2. Each client (tenant) runs its own Medusa instance. Layers, dependencies pointing down only:

- **application** (`apps/backend`): which domains a tenant runs, via `composeApplication`;
- **domains** (`packages/domains/*`, Medusa plugins): a business capability combining modules (links, cross-module workflows and hooks, queries, storefront routes, admin pages and widgets);
- **modules** (`packages/modules/*`, Medusa modules): one bounded context each (tables, service, admin definition, translations, admin API), reusable by any domain;
- **platform**: `@repo/framework` (SDK) and `@repo/dashboard` (admin UI kit).

## Layout

Turborepo + Yarn 4 (node-modules linker), Node >= 20.

```
apps/backend/                 Medusa app (workspace "backend"): config (composeApplication), scripts, no domain code
packages/framework/           @repo/framework — platform SDK, built to dist/ (cjs for Node, esm for Vite)
packages/ui/dashboard/        @repo/dashboard — admin templates, form engine, data table (source-linked)
packages/modules/<name>/      @repo/module-<name> — reusable Medusa module (today: vehicle, fitment, parts, garage)
packages/domains/<name>/      @repo/domain-<name> — business domain, a Medusa plugin (today: automotive)
packages/config/              @repo/config — tsconfig (module.json, layer.json), eslint (layers.js, module-boundaries.js), jest presets
packages/tooling/scripts/     @repo/scripts — layout spec + check-layout, gen-module, gen-domain, module-db-generate, domain dev watcher
infra/docker, infra/k8s       local infra and Kubernetes manifests (target: Kubernetes on OVHcloud)
infra/n8n/                    n8n workflow: AI agent researching the vehicle catalog (generated by build-workflow.mjs)
```

`@repo/framework` entries: `entity`, `core`, `utils`, `admin`, `medusa` are isomorphic (safe in admin code); `entity/server`, `http`, `orm`, `admin/plugins` are server-only.

### Package layout: contract → core → adapters

Every module and domain is layered; dependencies point down only, and adapters never import each other:

- **contract** (isomorphic): what the package promises: manifest, entities, types and request schemas, ports (the sockets a domain plugs adapters into), translations. The only part of a module other modules may import.
- **core** (isomorphic): the package's rules as pure functions (no I/O, no Medusa runtime), fully unit-testable. Optional.
- **adapters**: `server/` (the Medusa module) and `admin/` (definition; React in `admin/ui/`). In a domain, Medusa's plugin folders are its adapters.

**Module** (`packages/modules/<name>`, entries in parentheses):

```
src/contract/        iso     ("./contract")  index.ts, manifest.ts (MODULE key + defineModuleManifest),
                                             entities/<entity>.ts (one defineEntity each) + enums.ts/shared.ts + index.ts,
                                             types/request schemas (e.g. conditions.ts), ports.ts, i18n/{en,fr,ar,index}.ts
src/core/            iso     ("./core")      <capability>/…: pure rules (fitment: conditions/, matching/)
src/server/          server  (".")           index.ts (Module + re-exports incl. routes), service.ts (thin: load → core → persist),
                                             models/<module>.ts, migrations/, hooks.ts (onEntity rules on own rows), http.ts
src/admin/           iso     ("./admin")     index.ts, module.ts (defineModule) — no React
src/admin/ui/        admin   ("./admin/ui")  React (components, hooks, detail sections); source only, never built
src/__tests__/                               mirrors the layers (core/*.unit.spec.ts, …)
```

Modules build with `tsc` to CommonJS + declarations in `dist/`; Medusa resolves `"."` (`dist/server/index.js`) and runs `dist/server/migrations`. Iso and admin entries carry an `import` condition pointing at `src/` so the admin's Vite build compiles them from source (like `@repo/dashboard`); Node and TypeScript use `dist/`. The exports map is derived from the layout (`yarn check-layout --fix`). Inside `admin/ui`, import the package's own entries (`@repo/module-<name>/contract`, `/core`), not relative paths.

**Domain** (`packages/domains/<name>`, a Medusa plugin; Medusa discovers `api/`, `links/`, `workflows/`, `subscribers/`, `jobs/`, `admin/` by path):

```
src/contract/        iso     ("./contract")  manifest.ts (defineDomainManifest), i18n/ (domain messages + toAdminI18n of its modules)
src/core/            iso                     domain rules (automotive: condition-attributes.ts, the vehicle catalog)
src/composition/     iso                     composition root: compose<Domain>() plugs domain adapters into module ports;
                                             called by workflows/hooks/composition.ts (server) and admin/setup.ts (admin)
src/queries/         server                  cross-module reads (behind interfaces when they may move to a search engine)
src/workflows/       server                  cross-module writes; hooks/: onEntity hooks across modules, composition.ts
src/links/ subscribers/ jobs/ scripts/       server (only when used)
src/api/             server                  handlers only: middlewares.ts, request.ts (request accessors),
                                             admin/<module-path>/[entity]/… mounts, store/<area>/route.ts, store/validators.ts
src/admin/           admin   ("./admin")     i18n/index.ts (re-export: Medusa's path), setup.ts, hooks/, routes/<module-path>/, widgets/
integration-tests/   http/*.spec.ts, helpers/
```

## Building a capability

1. `yarn gen:module invoicing --entity Invoice --path invoices` (a reusable module), then `yarn gen:domain billing --modules invoicing` (or mount it in an existing domain), and follow the printed steps. The app runs a domain by adding its manifest (`@repo/domain-<name>/contract`) to `composeApplication({ domains: [...] })` in `apps/backend/medusa-config.ts`; that registers the domain's modules too, dependencies first, and fails at boot on a missing one.
2. Declare entities with `defineEntity` in the module's `src/contract/entities/` (one file per entity: scalar Zod schema + `relations: (r) => ({ … })`; enums in `enums.ts`, shared fields in `shared.ts`), and add them to `defineEntities` and to the `EntityRegistry` augmentation in `entities/index.ts`. Columns follow Medusa's property types (https://docs.medusajs.com/learn/fundamentals/data-models/properties): `z.string()` → `text`, `z.number().int()` → `number` (integer), `z.number()` → `float`, `fields.bigNumber()` → `bigNumber` (numeric, plus `raw_<field>`), `z.boolean()`, `z.date()` → `dateTime`, enums → `enum`, `z.array(z.string())` → `array` (`text[]`), other arrays, objects and records → `json`; `.nullable()`/`.optional()` and `.default()` carry over; unique and other indexes, and checks (SQL or `(columns) => sql`), are entity options. Own text fields in `search` (default: the label's) are also `searchable()` for Medusa's `q`; `fields.translatable()` marks text `translatable()` for Medusa's Translation module: the `translation` feature flag is on (app and domain test configs), Medusa creates the entity's translation settings at startup (Settings › Translations), and store responses built by the domain's `storeProducts` are translated to the request's locale (`?locale=fr-FR` or `x-medusa-locale`, codes from the Translation module's locales) with `applyTranslations`; translatable today: fitment position `name`, `category`, fitment `notes`. Optional: `label: { fields, format }` for how records read in pickers, relation cells and titles (fields may traverse relations, e.g. `model.make.name`); `fields.image()` for image URLs with an upload widget; `fields.localized()` for text in several languages. `messages: { unique: [{ on, message }], constraints: { name: message } }` gives readable errors for unique indexes and check / exclusion constraints (unique ones default to "A <entity> with this <columns> already exists."). `derived: { field: { from, compute } }` computes columns on every write (search keys, slugs; filters on them are normalized the same way); `readOnly: [...]` keeps server-managed fields out of the DTOs. Relations to other modules use `r.link(Target)`: stored in a Medusa link table by default, or as an indexed `${key}_id` column with `{ storage: "column" }` plus a read-only `defineLink` in the domain's `src/links/` (preferred for high-volume rows). Medusa models are declared with `defineEntity(Name, { schema, label, external: { module, url } })` so they can be link targets and pickers; the common ones (`ProductVariant`, `ProductOptionValue`, `Customer`) are in `@repo/framework/medusa`.
3. Rules go in `src/core/` as pure functions (by capability); the service (`src/server/service.ts`) loads, calls core, persists, and never resolves another module. Models: `src/server/models/<module>.ts` exports `toModels(entities)` (Medusa only discovers models in non-index files of `models/`).
4. API: the module's `src/server/http.ts` lists exposed entities in `createEntityRoutes({ entities })` (re-exported from `.`); the domain's route files (`src/api/admin/<path>/[entity]/…`) and middlewares mount it in one line each.
5. Admin: each module exports its definition from `@repo/module-<name>/admin` (`src/admin/module.ts`: `defineModule({ path })`, one `m.crud(Entity, { path?, label?, steps?, relations? })` per feature) and its translations from its contract (`src/contract/i18n/`: `defineTranslations(path, { en, fr, ar })`, `fr`/`ar` typed `SameShape<typeof en>` so a missing key fails `tsc`). The domain's `src/contract/i18n/index.ts` exports `toAdminI18n(...modules, domain)` (re-exported by `src/admin/i18n/index.ts`, where Medusa looks); its route pages mount a module with `translatedMenu(definition)` and `translationNs: "translation"` spelled out (Medusa reads it statically). Labels resolve through `useLabels()` (`entities.<Name>.fields|values`, `modules.<path>.features|steps`). Everything the admin shows is translated (en, fr, ar):
   - dashboard text uses Medusa's own `actions.*` / `general.*` keys for plain words, and `erp.ui.*` (`COMMON_MESSAGES` in framework core) for sentences; read them with `labels.action(…)` / `labels.ui(key, vars)`;
   - module UI text goes in its messages (`modules.<path>.messages.*`, `i18nKeys.message`);
   - a domain ships its own translations the same way (automotive: `src/contract/i18n/automotive.ts`, read with `useDomainText()`);
   - record labels take a `LabelContext` (`format(row, ctx)`: `ctx.value(entity, field, value)`, `ctx.text(key, fallback)`); render them with `labels.record(entity, row)`, and pass `ctx` on to nested formats;
   - fitment conditions take `ConditionTexts` (`summarizeConditions(tree, texts)`, `validateTree(tree, texts)` from `@repo/module-fitment/core`; admin: `useConditionTexts()`), and catalog attributes carry `i18n` keys;
   - text written by the server in several languages is a `fields.localized()` field (`{ en, fr, ar }`, JSON column; the admin shows the user's language via `<LocalizedText>`, store routes pick `req.locale`, i.e. `?locale=` or `x-medusa-locale`, with `localizedText`). Server code translates with `translator(resources, locale)` over the domain's resources. Example: fitment's `conditions_summary`, written in every locale from the translations the domain plugs in (`provideConditionTranslations`); after translation changes run the domain's `refresh-condition-summaries` script (from `apps/backend`: `npx medusa exec ../../packages/domains/automotive/.medusa/server/src/scripts/refresh-condition-summaries.js`).

   Still English on the server: API error messages and record labels in store responses. Entity sets declare their API path (`defineEntities(..., { module, path })` → `/admin/<path>/<entity>`), so pickers reach entities of other modules.
6. Run the module's `db:generate` after entity changes and commit the migration.
7. Each module's `src/contract/manifest.ts` exports its key and `defineModuleManifest({ key, dependsOn, resolve })` (keep `key` and `dependsOn` literal, the boundary rule reads them). A module imports only its own files, platform and third-party packages, and the contract of a module listed in `dependsOn` (`@repo/module-<dep>/contract`); never a domain or a file outside its package. When a module needs something only the domain knows, its contract declares a port (`ports.ts`) and the domain's composition root plugs the adapter in: e.g. fitment's `provideConditionAttributes` / `provideConditionTranslations` (`@repo/module-fitment/contract`), fed by the automotive catalog (`src/core/condition-attributes.ts`) and translations in `composeAutomotive()` (`src/composition/`), called by `src/workflows/hooks/composition.ts` and `src/admin/setup.ts` (imported by the pages and widgets that edit fitments).

Writes go through the framework's compensating workflows (`createEntitiesWorkflow`, …); DELETE is a soft delete. Linked ids (`r.link`) are checked on write: an unknown target is a 400. List routes accept `?q=` (every word must match one of the entity's `search` paths, by default its label's text fields). Records pointing at Medusa models are cleaned up when those are deleted (automotive: `removeOrphansWorkflow` in `src/workflows/remove-orphans.ts`, run by `src/subscribers/medusa-deletions.ts` and the one-off `src/scripts/remove-orphans.ts`). To do more on a write (e.g. keep a Medusa record in sync), register `onEntity(Name, { created, updated, deleting, deleted })` from `@repo/framework/entity/server`: hooks run inside the same workflow step, with compensation. Rules within one module go in the module's `src/server/hooks.ts` (imported by its `index.ts`) and call its service; hooks spanning modules go in the domain's `src/workflows/hooks/` (Medusa's workflow loader imports them). Cross-module logic lives in the domain's workflows (writes), hooks and `src/queries/` (reads); route handlers only validate, call a service, workflow or query, and respond. Storefront routes live in the domain's `src/api/store/` (Medusa requires a publishable key; only published products in the key's sales channels are returned). Detail pages take extra panels via `<Module sections={{ featureKey: [{ id, render }] }}>` in the domain's admin route page (module UI comes from `@repo/module-<name>/admin/ui`); `hideInDetails` in a feature's overrides drops a field from the detail attributes. Admin widgets listing a parent's records use `<EntityPanel module feature parent={{ field, value }} rowActions? />` from `@repo/dashboard/module`.

## Rules enforced in CI

- **Layer projects** (`tsc -b tsconfig.check.json`, preset `@repo/config/ts/layer.json`): each package's iso layers (module: contract, core, admin definition; domain: contract, core, composition) form a project with no Node or DOM types; the server and admin UI projects reference it. Importing a file of a layer that isn't referenced fails to compile.
- **Layers** (`packages/config/eslint/layers.js`): framework never imports UI, modules or domains; isomorphic framework files never import server code; isomorphic layers of modules and domains import no server-only Medusa or framework package and no React/UI library; UI packages and admin code use only isomorphic framework entries and admin-safe Medusa packages (`@medusajs/ui`, `icons`, `admin-sdk`, `js-sdk`, `framework/zod`); only apps import domains; server code of domains and modules never imports UI packages. Module boundaries (`packages/config/eslint/module-boundaries.js`): modules import only their own files and declared dependencies' contract, never a domain (see step 7). Type-only imports are always allowed.
- **Layout** (`yarn check-layout`, spec in `packages/tooling/scripts/src/layout.mjs`): allowed `src` folders, required files, kebab-case names, one entity per file, no READMEs in `src`, exports derived from the layout.
- **Versions** (`yarn.config.cjs`): Medusa core packages pinned to one version (change `MEDUSA` there to upgrade), plus React, react-router-dom, zod; every other dependency uses one range across workspaces; internal packages use `workspace:*`.

## Testing

- Jest presets: `@repo/config/jest/base.cjs` (all packages), `@repo/config/jest/medusa.cjs` (apps, modules, domains; maps `@repo/module-<name>` to its `src/server` and `@repo/module-<name>/<entry>` to `src/<entry>`).
- `TEST_TYPE` selects the suite: `unit` (`src/**/__tests__/**/*.unit.spec.ts`), `integration:http` (`integration-tests/http/*.spec.ts`), `integration:modules`.
- Core rules get pure unit tests in the module (`src/__tests__/core/`); behaviour that needs a database is tested through a domain's integration tests.
- Integration tests use `medusaIntegrationTestRunner` and a per-worker temp database (dropped afterwards). Admin auth: `adminHeaders(getContainer())` from `@repo/config/jest/medusa-helpers.cjs`.
- Env: committed defaults in `.env.test.example` (match `infra/docker` defaults); put personal overrides in `.env.test` (git-ignored).
- Domains carry a test-only `medusa-config.ts` that loads their modules from source (`src/server` of each module in `src/contract/manifest.ts`), so the runner and the tests share one instance of each module.

## Conventions

- Prettier with default settings (no config file); ESLint flat configs extend `@repo/config/eslint/base.js`.
- Domain and module source use relative imports (or package entries), not `~/…` aliases: the built output keeps aliases and production Node can't resolve them.
- Medusa imports use sub-paths (`@medusajs/framework/utils`, `/workflows-sdk`, `/zod`, …).
- Derive types from schemas: `InferEntity<typeof Entity>`, `z.infer<typeof Schema>`; don't hand-write duplicates.
- Files kebab-case (checked by `check-layout`); entities and React components PascalCase; module keys `UPPER_SNAKE_CASE` constants in `contract/manifest.ts`.
- Admin code must not import server code (see Layers); `@repo/dashboard` is admin-only.

## Production notes

- `apps/backend/Dockerfile` (context: repo root) prunes the `backend` workspace, builds with turbo and copies built framework, module (`dist`) and domain (`.medusa`) artifacts next to `node_modules`.
- Medusa enables database SSL in production mode; local databases without SSL need `?sslmode=disable`.
